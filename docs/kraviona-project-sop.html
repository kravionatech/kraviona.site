Kraviona Platform Architecture & SOP

This document explains how the complete blog platform is structured, how requests and data move through it, how editors and administrators publish safely, and how the system is developed, tested, deployed and recovered.

Version 2.0 Updated 9 August 2026 Owner: Kraviona Engineering Classification: Internal

1. Platform overview

Kraviona is a MongoDB-backed editorial platform composed of a public publication, an administrator studio, a contributor editor, an Express API and an MCP automation service.

Public

Reader website

Search-indexable Next.js site containing the homepage, journal, category pages, services, newsletter and guest-post application.

Private

Admin studio

Administrator-only workspace for posts, categories, contributors, comments, subscribers, services, enquiries, AI and global settings.

Contributors

Editor workspace

Approved editors create rich-text stories, manage SEO and publish within their assigned backlink allowance.

Core

Backend API

Express application implementing authentication, validation, business rules, database access, uploads, email and automation.

Automation

MCP server

Exposes 38 typed tools over local stdio or authenticated Streamable HTTP for agents and approved MCP clients.

Data

MongoDB & providers

MongoDB stores platform data. Cloudinary handles images, Resend handles newsletter email and Anthropic generates optional drafts.

Current commercial rule: the payment gateway and article paywall are removed. Published journal content is public. Guest posting is free during the configured campaign; editorial and safety standards still apply.

3. System architecture

Reader ──────────────► Client Next.js ───────┐ Administrator ───────► Admin Next.js ─────────┤ Approved editor ─────► Editor Next.js ────────┼──► Express API ───► MongoDB MCP client ──────────► MCP stdio/HTTP ────────┘ │ ├──► Cloudinary (images) ├──► Resend (email) └──► Anthropic (drafts) Public discovery: Client ─► robots.txt / sitemap.xml / feed.xml / llms.txt / ai.txt

Backend request lifecycle

  1. Express receives the request and checks whether its browser origin is allowed by CORS.
  2. JSON is parsed with a 10 MB limit and cookies are made available.
  3. Protected routes verify the access JWT; role middleware enforces administrator or editor access.
  4. Zod and route-level checks validate input, ownership, word limits, link limits and referenced IDs.
  5. Mongoose performs database reads/writes and schema hooks calculate derived values such as word count.
  6. The route returns JSON; central error middleware returns a consistent { "error": "message" } response.
Canonical host rule: production URLs must come from explicit environment variables or https://kraviona.site. Never create production links from localhost, a request Host header, or an undefined setting.

5. Business workflows

Administrator-created story

  1. Create or choose category.
  2. Create post as draft.
  3. Add semantic HTML, summary, author, media, takeaways, FAQs and SEO.
  4. Preview and verify facts/links.
  5. Set status to published.
  6. Confirm the public URL, sitemap and social preview.

Editor direct publishing

  1. User requests an editor account.
  2. Admin approves the editor and backlink allowance.
  3. Editor signs in and writes in Tiptap.
  4. Client checks title, category, 300–2,500 words and link allowance.
  5. API sanitizes and validates again.
  6. Publishing creates the contributor record and the public journal post.

Reviewed guest-post path

  1. Submission remains draft/submitted.
  2. Admin reads full content and outbound links.
  3. Admin approves or rejects with private notes.
  4. Publishing calls the shared public-post helper.
  5. Helper prevents duplicate public slugs and increments category count once.

AI draft workflow

  1. Admin supplies a topic and category.
  2. AI service requests strict JSON.
  3. Zod validates title, HTML, takeaways, FAQs and SEO limits.
  4. Manual generation remains draft/noindex.
  5. A human verifies facts, originality and sources before publishing.

Newsletter workflow

  1. Reader submits email.
  2. Subscriber is stored as pending.
  3. Resend sends a confirmation link.
  4. Token confirmation changes status to subscribed.
  5. Admin may unsubscribe; delete only for explicit removal requests.

Client enquiry workflow

  1. Public form validates contact information and honeypot.
  2. Inquiry begins as new.
  3. Admin moves it through contacted, qualified and closed.
  4. Spam is classified instead of mixed with active leads.
  5. Private notes must remain factual and necessary.

7. MCP server

The MCP server is an authenticated adapter. It contains no direct database credentials and never bypasses backend authorization or validation.

Local stdio

The MCP host starts src/index.js. Tools call the configured API URL. This is the simplest local development option.

Remote HTTP

src/http.js creates stateful Streamable HTTP sessions. Static bearer auth and OAuth DCR + PKCE protect /mcp.

Tool groups

Domain Tools
System cms_health, get_dashboard_summary
Posts list_posts, get_post, create_post, update_post, set_post_status, delete_post
Guest posts list_guest_posts, get_guest_post, review_guest_post, delete_guest_post
Moderation/audience list_comments, moderate_comment, delete_comment, list_subscribers, save_subscriber, update_subscriber_status, delete_subscriber
Access list_users, create_editor_account, update_user_access
Taxonomy/services/leads Category, service and enquiry list/save/update/delete tools.
Settings/automation Site settings, crawler settings, AI draft and keyword queue tools.

Safe MCP operating sequence

  1. Call the relevant list/get tool and identify the exact record ID.
  2. Explain the intended change and preserve fields not in scope.
  3. Create content as draft unless publication is explicitly authorized.
  4. For deletion, require the caller to provide confirm: true.
  5. Read the record again after mutation and report the resulting status/URL.
  6. Do not place secrets in tool arguments except the temporary password required by account creation; transmit it separately and rotate it.

8. Local development SOP

  1. Install Node.js 22 and a reachable MongoDB instance.
  2. Run npm install at the repository root.
  3. Copy backend/.env.example to backend/.env and replace every required placeholder.
  4. Use long independent JWT access and refresh secrets. Add explicit client/admin/editor URLs.
  5. Run npm run bootstrap:admin -w backend if an initial administrator is required.
  6. Start all applications with npm run dev, or start workspaces individually.
  7. Open client 3000, admin 3001, editor 3002 and verify backend /health on 4000.
  8. Run builds and tests before committing.

npm install

9. Editorial SOP

Before publication

  • Confirm the search intent and reader problem.
  • Verify every factual claim and cited source.
  • Check originality and image usage rights.
  • Use one clear H1/title and logical H2/H3 headings.
  • Write a useful summary and descriptive image alt text.
  • Inspect every external link and avoid manipulative anchors.
  • Complete title and description without stuffing keywords.

After publication

  • Open the canonical public URL.
  • Check mobile layout, images and links.
  • Confirm indexability and sitemap inclusion.
  • Verify structured data contains no undefined/incorrect values.
  • Monitor corrections, comments and traffic quality.
  • Update stale facts and timestamps honestly.
Ranking rule: no workflow can guarantee a top Google position. Optimise for usefulness, accuracy, crawlability, reputation and legitimate internal/external references—not keyword repetition or doorway content.

10. Deployment SOP

  1. Create separate services/projects for client, admin, editor, backend and remote MCP as required.
  2. Set production environment variables in the hosting provider, never in committed files.
  3. Set NEXT_PUBLIC_API_URL=https://api.kraviona.site/api for browser applications.
  4. Set explicit backend CORS origins for every real frontend domain.
  5. Run backend tests, MCP contract tests and all Next.js production builds.
  6. Deploy backend first and confirm /health.
  7. Deploy frontends and verify authentication cookies work cross-origin over HTTPS.
  8. Deploy MCP with a separate bearer secret and verify /health, OAuth metadata and tool discovery.
  9. Run post-deployment smoke checks and record the release time/commit.
Production protection: never use localhost fallbacks in production settings. Never expose MongoDB, JWT, provider or MCP administrator credentials through NEXT_PUBLIC_* variables.

11. Security SOP

  • Use independent random secrets for JWT access, JWT refresh and MCP bearer authentication.
  • Use HTTPS for every production origin.
  • Restrict CORS to exact known origins.
  • Keep authentication cookies HTTP-only and secure in production.
  • Grant least privilege: reader, editor, administrator.
  • Suspend compromised editors immediately.
  • Keep backlink limits intentional and documented.
  • Validate file type, data URI and maximum upload size.
  • Sanitize guest HTML and disallow scriptable elements/protocols.
  • Never log passwords, tokens, raw cookies or API keys.
  • Rotate secrets after exposure or staff access changes.
  • Review dependencies and lockfile changes before release.
  • Require explicit confirmation for destructive MCP tools.
  • Keep admin, editor, backend and MCP pages out of search indexes.

12. Backup and recovery SOP

  1. Schedule encrypted MongoDB backups with a retention policy appropriate to the business.
  2. Export Cloudinary asset inventory or retain provider-side versioning.
  3. Store backups outside the primary application account/region.
  4. Test restoration into an isolated non-production database at least quarterly.
  5. Record recovery point objective (acceptable data loss) and recovery time objective.
  6. Before destructive migrations, take and verify a fresh backup.
  7. After restore, rotate environment secrets if the incident involved access compromise.
  8. Verify counts for posts, users, subscribers, guest posts and enquiries before reopening writes.

Deletion policy: status changes are preferred for operational records. Permanent deletion is reserved for explicit legal/privacy requests, confirmed spam cleanup or approved data-retention procedures.

13. Incident response

Severity Examples Immediate response
P0 Critical Secret leak, database exposure, destructive unauthorized publishing. Disable affected service, revoke/rotate secrets, preserve evidence, restrict access and begin recovery.
P1 High Authentication failure, API unavailable, mass broken content. Freeze deployments, inspect health/logs, rollback safe release or restore service.
P2 Medium Single workflow broken, upload/email/AI provider failure. Disable affected optional feature, communicate workaround and create fix.
P3 Low Visual issue, non-blocking copy or analytics problem. Record reproduction, prioritise and fix through normal release flow.
  1. Detect and record timestamp, symptoms, affected URLs/users and recent changes.
  2. Contain without destroying logs or evidence.
  3. Rotate compromised credentials and terminate invalid sessions.
  4. Recover using a verified rollback, configuration fix or backup.
  5. Validate critical user journeys and data counts.
  6. Write a blameless post-incident review with cause, impact and prevention actions.

14. Human-readable code standards

  • One responsibility per module or component.
  • Use descriptive names instead of single-letter variables.
  • Prefer early returns for validation and errors.
  • Centralise repeated response/error/query helpers.
  • Group routes and MCP tools by business domain.
  • Use comments to explain why, not obvious syntax.
  • Keep user-facing errors actionable and specific.
  • Validate at the trust boundary with Zod or explicit checks.
  • Do not silently swallow operational errors.
  • Keep production URLs in a single canonical helper.
  • Format JavaScript, TypeScript, JSX, JSON, CSS and Markdown with Prettier.
  • Add or update tests whenever tool contracts or business rules change.

15. Release checklist

  • Scope and acceptance criteria are documented.
  • No unrelated user changes were overwritten.
  • All touched code is formatted and understandable.
  • Backend syntax and automated tests pass.
  • Client, admin and editor type checks/builds pass.
  • MCP syntax and 38-tool contract tests pass.
  • Destructive operations require explicit confirmation.
  • No secret or production credential is present in Git diff.
  • Canonical URLs and CORS domains are correct.
  • Database migration has backup and rollback steps.
  • Critical flows were smoke-tested.
  • Documentation and environment examples are updated.
  • git diff --check passes.
  • Post-deployment health and public URLs are verified.

16. Troubleshooting guide

Symptom Likely cause Checks
Frontend calls localhost in production Missing/malformed NEXT_PUBLIC_API_URL or unsafe fallback. Inspect hosting environment, rebuild frontend, check generated network requests.
CORS blocked origin Exact frontend origin absent from backend environment. Verify protocol, host, port and trailing-slash normalization.
Editor cannot sign in Pending/suspended editor, wrong credentials or cookie domain issue. Check user status, backend response and HTTPS cookie behavior.
Guest story not public Record not published or public Post missing. Read guest status, retry publish, verify public slug and category count.
MCP tool returns admin login error Missing MCP API credentials or non-admin account. Check three KRAVIONA_* variables and backend login.
MCP HTTP returns 401 Missing/invalid bearer or expired OAuth access token. Check Authorization header, MCP secret and OAuth metadata/token flow.
Image upload fails Cloudinary missing, unsupported type or image too large. Check provider URL, image MIME type and 7 MB editor limit.
AI draft fails Missing provider key, invalid model response or validation failure. Check key/model, backend logs and strict JSON/word-count requirements.
Newsletter confirmation fails Expired/invalid token or email provider problem. Check subscriber record, Resend configuration and callback URL.
